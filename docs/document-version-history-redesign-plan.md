# 文档历史版本整改方案

## 1. 方案结论

将“文档版本”拆成两个明确概念：

- `project_documents.version` 只承担自动保存的乐观锁，每次正文保存递增，不向用户展示。
- `project_document_revisions` 只保存可阅读、可恢复的历史快照，以“持续编辑每 10 分钟一个快照、停止编辑 2 分钟后补一个最终快照”为固定颗粒度。

历史版本由服务端统一生成，前端不再通过离开文档时的 `createRevision` 决定是否留档。历史界面改为“右侧版本列表 + 主编辑区只读预览”，恢复历史版本会创建新的当前版本，不覆盖或删除已有历史。

## 2. 当前问题

- 自动保存每 800ms 更新一次文档版本，但只有 `flushSaves()` 恰好遇到未保存状态时才请求创建修订版；文档已自动保存后再离开页面不会生成历史，导致历史长期只有初始版本。
- 历史快照的生成依赖前端路由切换和组件卸载，关闭标签页、长时间停留或异常中断都无法稳定留档。
- 历史列表只显示内部版本号、标题和时间，没有编辑人；选择版本后列表被预览替换，无法连续浏览多个时间点。
- 420px 侧栏同时承担列表和正文预览，正文缺少足够阅读宽度，历史功能虽有入口但难以实际使用。

## 3. 版本颗粒度

### 3.1 固定规则

1. 创建文档时保存初始快照。
2. 用户持续编辑期间，距离该文档最后一个快照满 10 分钟后，在下一次成功保存时写入当前快照。
3. 文档连续 2 分钟没有新保存且当前 `version` 尚未进入历史表时，由服务端定时任务写入本轮编辑的最终快照。
4. 编辑人发生变化时，在新编辑人的首次保存前先固化上一编辑人的当前状态，避免不同编辑人的内容被归到同一条历史记录。
5. 恢复前先固化尚未进入历史表的当前状态；恢复成功后立即把恢复结果写成新的历史快照。恢复始终可再次撤销。
6. 标题和正文都未变化时不生成快照；同一 `document_id + version` 只能存在一条快照。

该颗粒度直接采用 Notion 已验证的自动历史模型：活跃编辑每 10 分钟记录一次，最后一次编辑 2 分钟后再记录一次。它既避免按 800ms 自动保存制造大量无意义版本，也不会把一次长时间编辑压缩成单个不可定位的结果。

### 3.2 数据语义

沿用 `project_document_revisions` 现有快照表，不新增第二条历史数据路径：

| 数据 | 唯一语义 |
|---|---|
| `project_document_revisions.id` | 对外 `revisionId`，历史记录唯一标识 |
| `project_document_revisions.version` | `sourceVersion`，生成快照时对应的文档乐观锁版本 |
| `title`、`content_json` | 可恢复的完整文档快照 |
| `editor_id` | 该快照所属的最后编辑人 |
| `created_at` | 快照生成时间，也是历史列表的排序依据 |

历史详情和恢复接口统一按 `revisionId` 定位，不再把内部 `version` 当作历史记录标识。编辑人名称由用户表用户名唯一映射到历史 DTO 的 `editorName`，前端只读取该字段，不从项目成员列表补齐或回退。

## 4. 服务端整改

### 4.1 快照生成

- 删除 `UpdateProjectDocumentRequest.createRevision` 以及前端 `pendingRevision`、离开页面补版本的逻辑。
- 文档更新事务继续只处理标题、正文和乐观锁；保存成功后调用统一的 `DocumentRevisionSnapshotService` 判断是否达到 10 分钟边界。
- 新增每分钟执行一次的历史快照任务，查询“最后更新已满 2 分钟且当前版本未快照”的文档；逐文档加行锁并重新判断后插入最终快照。
- 编辑人切换、恢复前固化、恢复后留档全部复用同一个快照服务，任何入口都不得直接拼装 revision 数据。
- 历史快照永久保留。本期不引入套餐、保留天数或清理配置。

### 4.2 接口

- `GET /project-documents/{documentId}/revisions`：返回按时间倒序的 `revisionId`、`sourceVersion`、`title`、`editorId`、`editorName`、`createdAt`。
- `GET /project-documents/{documentId}/revisions/{revisionId}`：返回指定完整快照。
- `POST /project-documents/{documentId}/revisions/{revisionId}/restore`：携带当前文档 `expectedVersion`，恢复后返回新的当前文档。

删除按版本号读取和恢复的旧接口语义，不保留双路由、双字段或兼容映射。

## 5. 前端交互整改

### 5.1 历史模式

- 打开“历史版本”时先完成当前自动保存，再进入历史模式。
- 右侧固定展示 320px 版本列表，主编辑区展示选中版本的完整只读正文；列表不会因选择版本而消失。
- 列表顶部固定“当前版本”，其下按“今天 / 昨天 / 日期”分组展示历史快照。
- 每条历史记录主信息为编辑人和时间，标题作为次要信息；不再突出内部版本号。
- 默认选中当前版本。选择历史快照后，主编辑区顶部显示“某人在某时保存的版本”，底部主操作为“恢复此版本”。
- 恢复前明确提示“当前内容会先保存为历史版本”；恢复成功后退出历史模式并回到可编辑的最新文档。

### 5.2 状态与边界

- 历史为空时仍展示当前版本，并说明历史会在编辑过程中自动生成。
- 加载失败保留当前文档，不清空主编辑区；版本列表原位提供重试。
- 历史详情加载失败只影响选中项，列表继续可用。
- 恢复期间锁定重复操作；遇到乐观锁冲突时停止恢复并要求重新加载最新文档。
- `Esc` 退出历史模式；键盘焦点保持在历史列表与关闭按钮之间可达。
- 本期只整改桌面端文档编辑页；移动端当前为只读文档页，不新增历史入口。

## 6. 实施范围

1. 后端收口快照生成策略与 revision 查询，移除客户端控制留档的参数。
2. 前端 store/API 改用 `revisionId` 单一路径，删除 `activeRevision` 对全局编辑状态的耦合。
3. 重构 `DocumentHistoryPanel` 为持久版本列表，并让 `DocumentsView` 控制主编辑区在编辑态与历史只读态之间切换。
4. 补齐编辑人、时间分组、当前版本、恢复确认及加载/冲突状态文案。
5. 更新 `docs/CONTEXT.md` 中 Document Revision 的定义，使“乐观锁版本”和“可恢复修订版”在领域术语中彻底分离。

## 7. 设计依据

- [Notion：Duplicate, delete & restore content](https://www.notion.com/help/duplicate-delete-and-restore-content)：活跃编辑每 10 分钟生成版本，最后编辑 2 分钟后补最终版本，并提供按时间选择和恢复。
- [Google Docs Editors：Find what's changed in a file](https://support.google.com/docs/answer/190843?hl=en)：历史修订允许合并，支持按编辑人查看、更早版本预览、恢复和命名版本，说明自动保存记录需要聚合为用户可理解的历史节点。
- [Confluence：Manage versions and revert content](https://support.atlassian.com/confluence-cloud/docs/manage-versions-and-revert-content/)：版本列表与版本恢复围绕完整页面快照展开，恢复动作产生新的当前版本，而不是删除后续历史。
